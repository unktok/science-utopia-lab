# 0026 — Joint system design loops and the recursive-improvement frontier

Date: 2026-10-31

The user's design object includes wiring, algorithms, rules, institutional
presence, timing and relationships, not just names or parameter values.
Longer term, the science system should be able to study and improve itself.
That motivation is recorded without calling an external optimizer recursive
self-improvement or claiming that repeated revisions guarantee improvement.

## Immediate engineering boundary

1. Atomic SystemSpec patches may jointly alter source, schemas, nodes, edges,
   schedules and parameters. Validate the finished transaction, not each
   intermediate half-protocol. No fixed institution catalog is introduced.
2. A persistent native outer loop commits suggestions before evaluation and
   actual observations before generating the next patch. Objective/model/world
   binding is separate from the mutable design. Technical failures have null
   loss; there is no unstated social veto.
3. A native-loss score-function route estimates gradients of a declared design
   distribution using full native evaluations. It does not replace the world
   with numeric equations and does not backpropagate through opaque native
   transitions. Exact tensor-backed world differentiation remains open.
4. Canonical replay and design-path exports share candidate fingerprints and
   actual observations. They are data for a game, not a claim that player-driven
   live installation and all new scientific activities are already implemented.

## Distinct long-term stages

- External optimization: an outside designer proposes scientific institutions.
- Endogenous institutional improvement: researchers/institutions inside the
  world propose versioned changes to their own system; another branch executes
  them against the declared objective; observations feed subsequent proposals.
- Recursive improvement of the improvement process: proposals can also change
  the designer, its memory, search strategy or institutional learning process.

The first has an executable outer loop. An initial second-stage bridge is also
QA-tested: an opt-in world observation exposes its SystemSpec, an institution
emits the SAME patch format, and a journal records proposal validity without
installing it or assigning a loss. The outer controller loads a hash-verified
native checkpoint and evaluates the last structurally valid proposal from the
incumbent's first development run as a fresh counterfactual world. QA source
lowers its own selection threshold after actual native rejections. This is
developer-authored behavior with scripted transport/corpus, not autonomous
LLM discovery or recursive improvement of the designer. The clean live pilot
at `7c91af2` exercises the external developer example only, not this later bridge.
No generated source is allowed to edit the host, evaluator, loss, raw evidence
or model credentials.
Hot installation into a running society requires explicit state migration,
causal version boundaries and replay/resume semantics; it is not implemented.
Loss changes are new experiments, not hidden "improvements" to reported scores.
World-model extensions are welcome but cannot be silently changed to make an
institution look better under a nominally fixed experiment.

## Breadth before scale

First exercise joint design, an actual native evaluation loop, a native-loss
gradient proposal path, and shared replay on a few systems/seeds. Do not wait
for larger population/seed budgets. A small numerical alternate world does not
satisfy this integration target. New hypotheses, experiments, datasets,
software, correction and new actor behavior remain explicit next work packages.
