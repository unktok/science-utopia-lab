# 科学システム最適化：立ち止まって設計を見直す

2026-11-07。ユーザーの「一回立ち止まってどうするか考えよう」に基づく整理。
新しい長時間実験は開始しない。元の研究者世界、過去の失敗、生ログは変更しない。

## 結論

研究対象は**自由に設計できる科学システム**であり、特定のローカルLLMにコード編集を
完遂させることではない。LLMは提案方法の一つであり、システム表現、候補生成、実行、
測定、損失計算、探索状態の更新を分ける。全面的な作り直しも、新しい最適化器の乱立も
行わず、既存の境界を再利用して不足する接続を明確にする。

元の研究者世界を包含・拡張する方針は変えない。微分可能な数値のおもちゃに置き換えず、
使える勾配・勾配推定・ブラックボックス評価を選ぶ。システムの自由度と探索方法は別軸。

## 1. 今回の事実と、説明の訂正

V44は2026-11-06T17:08:25Z開始、18:23:20Z終了、約75分。
8枠を消化し、6枠が評価完了、1枠が制度実行失敗、1枠が生成失敗。
独立検証も終了している。現在その実験は動いていない。
7件の提出成功と、6件の評価成功を混同しない。
物理world directoryは6件だが、失敗途中の世界を含み、既存checkpointの再利用もある。
したがって「6件の独立した成功した新規world」とは呼ばない。

| 目的 | 全4枠の結果 | 実際に起きたこと |
|---|---|---|
| `-Q+0.5R` | 12, 12, 実行失敗, 生成失敗 | 全件不採択が継続。後続2枠はnull |
| `-A` | -7, -7, -7, -7 | 全件採択が継続。後続ソースは空白変更または同一 |

- 効率G0は主に非有限スコアの除外を追加したが、観測された挙動は全件不採択。
- 効率G1は「平均査読点が8超なら強制採択」を追加した。実際の平均は3〜3.67で、
  その分岐は発火しなかった。Q=0、R=24のままなので損失は12。
- 効率G2は査読後の特徴列から低得点論文を除外した。これでは既に実行済みの査読件数は
  減らない。さらに投稿論文の判定が欠け、publicationの技術的整合性検査で失敗した。
- 効率G3は提出指定ターンにもreadを要求して拒否され、その次のpromptが240000-byte
  上限を超えた。16ターン中14回で終了し、予約した修復枠を実際には使えなかった。
  「修復枠を確保した」だけでは修復が可能なことの確認になっていなかった。

元の60efソースでG3の14ステップを再生すると、次のrecoveryターンの内部promptは
245925 bytes、まだ送信していない実wireは199047 bytesだった。内部promptは
`literal_editor_workbench`だけで45044 bytesを持ち、送信時にはこの重複workbenchを
除く既存rendererがある。ところが容量検査はrendererより前で行われる。
これはhostの内部表現上限による停止であり、GPU不足やモデルのtoken overflowを
観測したわけではない。実wireのtoken数・生成余裕は未測定で、送れば成功したとは
主張しない。[容量診断](results/native-search-context-size-review-v1.json)は14手の
原prompt/transition一致と30 raw JSONの不変を確認し、推論・制度コード実行は0。

提出形式の修正、静的検査の成功、コードの差分、挙動の差分、目的の改善は別の事実。
前回の「修正済み」は既知の提出・参照問題の修正であり、自動探索の実用性を証明した
ものではなかった。残った履歴容量問題も明記する。

### 事後の共通候補比較

既存の全採択結果を同じ効率損失で再採点すると、

`-22.333333333333336 + 0.5 * 21 = -11.833333333333336`

で、効率側の12より小さい。差は約23.83。ただし、**これは新しい最適化の改善ではない**。
既存auditorは既に両目的のcross-scoreを計算していた。
元のプロトコルは他armの結果を設計者へ渡さない独立探索であり、その分離はバグではない。
事後に他armの候補を見つけた結果を、当時の探索が発見したことにはしない。
この候補群では両目的とも全採択側を選ぶので、無理に目的ごとの違う勝者を作らない。

[再現可能な数値表](results/native-search-design-review-v1.json)は既存のcanonical
`evaluate_loss`で再計算した小さな派生物。新しいraw audit、候補bank、optimizer、実験ではない。
元のaudit/summaryのhash、全失敗枠、全同点候補、物理実行と論理評価の区別を保持する。

### 過去の成功を消さない

[V13](results/native-nested-search-v13-a1.md)には外部設計者の自由なコード改訂による
観測改善（throughput -7→-10、efficiency -17→-18）がある。
ただし設計者は自己申告の外部Codexであり、研究者Qwenによる自動発明ではない。
最近のV14〜V44は設計までローカルLLMへ自動化する別の試み。
「プロジェクト全体で一度も改善していない」「自由な制度を実行できない」は不正確。
またsource/world bindingが違う歴史的結果を、同じ予算の比較や現在の初期bankへ無断混入しない。

## 2. 元の全体目標に対する棚卸し

| 元の目標 | 残す実装・実績 | まだ実現・実証していないこと |
|---|---|---|
| 目的を変えて科学システムを最適化 | `LossSpec`、測定、ask/tell、native oracle、過去の目的別実験 | 安定した自動探索、目的ごとの有効な制度差、一般化・現実的科学価値 |
| 出来合いでない制度の発明 | 任意のsandboxed Python、生成IR、ports、state、typed native action | 強い自動発明者。形式や静的検査だけでは挙動を保証できない |
| 制度の有無・配線・過程を自由にする | `SystemSpec`、graph編集、protocol、dependency/guard/repetition、actor/artifact | native actionの信頼境界、年単位の物理法則、研究活動の簡略化は残る |
| 勾配等を使えるところで使う | 条件付きLR/LOO/補正付きcontrol variate、連続座標、tensor表現 | 勾配法の優位性・分散削減。任意コードや世界全体のJacobianではない |
| 継続的・再帰的な改善 | own-history redesign、別系統のsame-society adoption | 制度発明者自身や改善手続きが改善したという証拠 |
| ゲーム的UIと理解 | 英語のpixel/cyberpunk UI、canonical replay、Foundry/observatory | 完成した経営ゲームではない。演出は科学的活動の証拠ではない |

ゲームと論文は同じcanonicalな実験記録を読む。別のtoy世界を作る必要はない。
この見直しでは新しいゲーム画面や原稿の数値を先行して作らない。
各トラックを「バックグラウンドで永続的に動いている」とは説明しない。

## 3. 残す基盤と整理する境界

| 責務 | 既存の部品 | 方針 |
|---|---|---|
| 何を設計できるか | `SystemSpec`、design patch、authoring IR、native capabilities | 維持。レビュー制度のメニューへ狭めない |
| どう提案するか | `blackbox.SearchSpace`、`AdaptiveRandomSearch`、生成器、mixed design | LLM、数値変異、構造編集、勾配提案を同じ候補境界へ |
| どう実行するか | `native_factory`、`native_world`、isolated code executor | 原研究者世界を唯一のnative評価境界として維持 |
| 何を測るか | native measurements、原review record、checkpointとprovenance | まず測定値を保存。生成したfinal_scoreを原査読点にしない |
| どう採点・選択するか | `loss.evaluate_loss`、`Observation`、ask/tell、incumbent | 目的別の探索状態を分離。宣言した損失だけで選ぶ |
| 勾配をどう利用するか | `native_factorized_gradient`、`native_expectation_estimators`、`native_adaptive_search` | 条件付き分布と微分対象を明示。新しい名の推定器は足さない |
| 過去の結果をどう使うか | `artifact_reuse`、audit cross-scores、`native_cost_bank` | raw保存・事後比較・事前宣言のwarm startを分離 |
| LLMの編集をどう完遂するか | `native_staged_author_v15`とV44 profile | bounded active contextと実際に使えるrepair経路を設計し直す |

`AdaptiveRandomSearch`等が存在することと、自由なnative生成器へ全て接続済みであることも
分ける。単一strategy、空のfactor/coordinate、count=1のV44では、LLMに次を提案させる
ことが探索の中心であり、数値・勾配の探索が自動的に働いていたわけではない。

```text
SystemSpec（設計自由度）
        ↓
提案器 → 技術的検査 → native実行 → 不変の測定記録
   ↑                                  ↓
   └──── 目的別の探索状態 ← LossSpecで採点
                                      ↓
                              同じ記録をUI・論文へ
```

技術的無効はnull。公平性・有用性・新規性等の隠れたvetoは加えない。
意味のない変異や同一挙動も記録するが、新制度の発明や改善とは数えない。
同じ損失だからprogramが同値だとは判定しない。

## 4. 「共通bank」と「独立探索」は違う実験

1. **固定した共通候補群の再採点**：同じ測定値を目的ごとに読む。順位と選択の検査。
   これだけで自動発明、最適化性能、held-out改善を主張しない。
2. **共通初期データからの目的別探索**：初期候補・利用可能な測定・新規評価予算を事前に
   揃え、その後はarm別の状態で提案する。他armの未来の結果は渡さない。
3. **途中でもデータを共有する探索**：別の明示的プロトコル。共有による情報優位と
   物理実行費用を計上し、独立探索と同じ比較として扱わない。

次の小規模検証では2を候補とする。bankは初期条件であり、探索空間の上限ではない。
候補・source/model/corpus/seed/fidelity・測定器・provenanceを結び付ける。
lossが実際のworld入力に影響する構成なら、その依存も実行identityに含める。
別の目的に必要なmetricが未測定なら再採点不可であり、推定やゼロ埋めはしない。
ここでは既存V44をwarm-start実験へ再解釈しない。

## 5. 次の作業を有限に区切る

| 段階 | 作業 | 終了条件／主張の境界 |
|---|---|---|
| R0：今回 | 終了したV44の再検証、再採点、元の目標・コード・失敗の棚卸し | 再現できる数値表、設計判断、現状更新。新規推論・worldは0 |
| R1：編集経路 | scalar loss/状態、現draft、直近エラーを優先したbounded active context。不要な重複workbenchを内部から除き、内部記録と実wireの予算を区別。古いsource/履歴はhash付きの読取可能artifact | 実際のG3履歴で最後のrepair→finishのpayloadを構成・再生できる。byteだけでなく実wire/token予算も検査 |
| R2：探索の接続 | 既存ask/tell・canonical lossに共通初期データと複数の提案器を接続 | 既知の測定結果で目的別の最小値・同点・null・restartが正しく再現される。新optimizerの成果とは呼ばない |
| R3：最小native検証 | 新source/profileの有限実機校正後、共通初期条件から各目的で最大1新規候補を提案・実行する案 | 最大2 world試行の前向きprotocolを別途凍結。既存best、提案内容、実測結果、費用を比較。失敗や非改善で枠を補充しない |
| その後 | 自由なsource/構造提案、使える勾配提案を同じ境界で検証 | 新しい制度の発明と条件付きパラメータ更新を区別。スケールはまだ増やさない |

R1は完全ログを消したり、生成コードを自動修正したりするものではない。実験中の
profile/sourceは変えない。新しい表現・選択・budgetの変更は前向きに宣言する。
R2の固定bankで期待損失が下がっても、既存`native_cost_bank`と同じく新規native bestの
発見ではない。R3の新しい候補が改善しなければ、その負の結果をそのまま残す。
有効な発明や一般化は研究上の結果であり、ソフトウェアの合格条件を満たすため捏造しない。

## 6. 今は行わないこと

- 同じLLM編集ループを、seedや候補数だけ増やしてもう一周すること。
- 外部高性能モデル、追加費用、model/backendの無断変更。
- 既存モジュールを捨てて新フレームワークへ移植すること。
- 目的ごとに違う制度や改善が出るまで続け、成功例だけを報告すること。
- 形式テストの件数、ソースhashの差、ゲーム演出を科学的改善の代わりにすること。
